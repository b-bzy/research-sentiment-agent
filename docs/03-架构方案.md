# 架构方案：研报多空打分 Agent

> 目标功能只有一个：**把各家期货公司的研报判成看多/看空/中性，汇总成「全市场偏多还是偏空」，按时间可比。**
> 设计原则：能少一个组件就少一个。

---

## 〇、前置假设

| 假设 | 如果不成立 |
|---|---|
| 内部系统，用户是交易员，几十人量级 | 用户上千则前端要独立部署，本方案不变 |
| 每日研报量在百篇量级（几十家 × 每家 1–3 篇） | 上千篇则打分环节要加并发队列 |
| 没有 Wind / iFinD 的研报 API 授权 | **有的话采集层可以砍掉大半**，直接从终端接口取 |
| 允许调用外部 LLM API | 不允许则换本地部署 Qwen / GLM，其余不变 |

---

## 一、整条链路

```
① 采集          ② 落地           ③ 解析          ④ 切分
官网 / 邮件  →  PDF + 元数据  →  MinerU      →  按品种切块
聚合站兜底      对象存储/磁盘     → Markdown     品种词典锚定

     ⑤ 打分              ⑥ 聚合             ⑦ 呈现
  →  规则 + LLM      →  净得分公式      →  盘前推送（企微/飞书）
     方向 + 置信度       日 / 周口径         Web 看板（多空矩阵 + 曲线）
     + 证据原句          品种 → 板块 → 大盘
```

每一环的选型如下。

## 二、① 采集：数据源怎么拿

### 数据源优先级

| 优先级 | 来源 | 形态 | 说明 |
|---|---|---|---|
| **主** | 各期货公司官网研究所栏目 | PDF 下载链接 | 最规范、有明确发布时间、可稳定抓取。永安、南华、中信建投期货、国泰君安期货、银河期货等主流机构都有 |
| **辅** | 机构客户邮件订阅 | 邮件附件 PDF | 很多期货公司只对客户发邮件。**开一个专用邮箱订阅，用 IMAP 收信取附件**，比爬官网还稳 |
| **辅** | 公众号 | HTML | 部分机构主渠道是公众号，需单独适配 |
| **兜底** | 聚合站（慧博投研、东方财富研报中心） | PDF / HTML | 官网抓失败时补齐，但发布时间可能失真，只作补漏 |

### 选型

| 项 | 选型 | 理由 |
|---|---|---|
| 爬虫框架 | **requests + BeautifulSoup**，每家一个适配器 | 几十家源、结构简单，上 Scrapy 是杀鸡用牛刀 |
| 反爬 | 限速 + UA 轮换 + 失败重试 | 期货公司官网反爬普遍很弱，不需要代理池 |
| 邮件收取 | Python `imaplib` | 标准库够用 |
| 调度 | **APScheduler**，每天 6:30 / 8:00 / 12:00 三轮 | 单机定时任务，不上 Celery |
| 去重 | **文件内容 MD5** | 同一篇会从多渠道重复抓到 |

> **不选 Scrapy / Celery / 代理池**：量级撑不起这些组件的复杂度，加了只是增加运维负担。

### 关键设计：两个时间戳

每条记录必须同时存：

- `publish_time` —— 研报上标注的发布时间
- `ingest_time` —— **进入本系统的时间**

**所有指标计算一律用 `ingest_time`。** 用 `publish_time` 会引入未来函数（周五发的报告周一才抓到，回测时却当成周五就有），这是研报类指标最容易犯也最致命的错误。

## 三、②③ 落地与解析：文档怎么处理

### 文档形态分布

| 格式 | 占比 | 处理方式 |
|---|---|---|
| PDF | ~90% | MinerU |
| HTML（网页版日报 / 公众号） | ~10% | trafilatura |
| Word | 极少 | python-docx，或直接人工转 PDF |

### 选型

| 项 | 选型 | 理由 |
|---|---|---|
| PDF 解析 | **MinerU**（opendatalab，≈79.6k star） | 输出带**标题层级**的 Markdown/JSON，这正是后面按品种切分的依据。期货日报是图文混排 + 大量表格，普通 pdfplumber 抽出来是一团乱码 |
| HTML 正文抽取 | **trafilatura** | 一行调用，正文识别准确率高 |
| 原件存储 | **本地磁盘 / MinIO**，路径入库 | 必须留原件，因为解析规则会迭代，需要能重跑 |
| 解析结果 | Markdown 文本存 DB | 便于人工核对与重跑 |

> **不上 OCR**：期货公司研报是电子生成 PDF，不是扫描件，MinerU 的文本层已经够用。真遇到扫描件的机构，单独标记走人工。

## 四、④ 切分：全链路最关键的一步

### 为什么必须切

一篇期货日报的典型结构是**多品种平铺**：

```
【贵金属】沪金沪银  行情回顾… 逻辑分析… 操作建议：暂不看空
【有色】沪铜        行情回顾… 逻辑分析… 操作建议：谨慎逢低偏多
【黑色】螺纹钢      行情回顾… 逻辑分析… 操作建议：逢低偏多思路为主
```

整篇打一个分，等于把三个不同方向的观点搅成一杯浆糊——RavenPack 官方文档也承认整块打分会把对立观点抹成中性。**必须切到「一个机构 × 一个品种 × 一个观点」的粒度。**

### 选型

**双重锚定：标题层级 + 品种词典**

1. 用 MinerU 输出的标题层级做一次粗切
2. 用**品种词典**在每块里匹配品种，做校验和归一

品种词典的形态（需要人工维护，是这个项目的核心资产之一）：

```
沪铜  →  别名: 铜, 电解铜 | 合约代码: CU | 板块: 有色
螺纹钢 →  别名: 螺纹, 建材 | 合约代码: RB | 板块: 黑色
```

3. 一块里匹配到多个品种 → 标记为「多品种块」，进一步按段落切或降权
4. 一块里匹配不到品种 → 标记为「宏观/综述块」，单独归类（**这类块其实很有价值，是对大盘的直接判断**）

> **不上 NER 模型**：品种是封闭集合（国内商品期货约 70 个），词典匹配的准确率高于模型，且完全可解释、可维护。

## 五、⑤ 打分：怎么判多空

### 三层漏斗

```
       ┌─ 规则命中（约 60–70%）──→ 直接出方向，置信度高
输入块 ┼─ 规则未命中 / 冲突 ──→ LLM 判断 ──→ 出方向 + 置信度
       └─ LLM 低置信度 ────────→ 进人工复核队列
```

**第一层：规则。** 期货日报的「操作建议」栏高度模板化，可以用句式模板覆盖一大半：

| 表述 | 方向 |
|---|---|
| 逢低偏多 / 多头思路为主 / 谨慎逢低偏多 | +1 |
| 前多持有 / 前多保护利润 / 暂不看空 | +0.5（偏多但保守） |
| 区间操作 / 短差操作 / 观望为主 | 0 |
| 逢高沽空 / 空头思路为主 | −1 |
| 谨慎追空 | **−0.5**（注意：是"别追空"，偏中性甚至偏多，容易判反） |

规则层必须配套**程度副词表 + 否定词表**（「不看好」「略偏空」「大幅回落」），可直接用开源的中文金融情感词典资源。

**第二层：LLM。** 规则没命中或多个规则冲突时调用。

- 选型：**DeepSeek / Qwen / GLM 的 API**（中文金融文本表现够用，成本远低于 GPT 系）
- 输出**强制 JSON**：`{方向: -2~+2, 置信度: 0~1, 证据句: "..."}`
- **必须要求返回证据原句**——这是后面可解释下钻的唯一来源，也是交易员追问「凭什么」时的答案

**第三层：人工复核。** 置信度低于阈值的进队列，人工判完的结果**回流成标注集**，用来迭代规则和 prompt。

### 三个必须做的设计

| 设计 | 原因 |
|---|---|
| **负面非对称加权** | 分析师不轻易喊空，正负等权会让指标长期漂在偏多区而失去区分度 |
| **打分结果不可变 + 记模型版本号** | 口径迭代后要能重算历史；不记版本，纵向可比性立刻失效 |
| **打分与聚合彻底分离** | 打分是一次性的（贵、慢），聚合是可反复重算的（便宜、快）。混在一起改口径就得全量重跑 |

> **不训模型**：百篇/天的量级，规则 + LLM API 完全够用。自己微调 BERT 要先攒几千条标注，投入产出比不划算。**先跑起来，标注自然会从人工复核队列里攒出来**，攒够了再考虑微调。

## 六、⑥ 聚合：怎么算成一个数

### 三级聚合

```
观点块  ──→  品种净值  ──→  板块净值  ──→  大盘情绪分
(带方向)     (同品种多家)    (同板块多品种)   (全市场)
```

**品种净值（baseline 公式，先跑这个）：**

```
品种净值 = (看多家数 − 看空家数) ÷ 总家数 × 100      # 范围 −100 ~ +100
```

**这条公式是必须先落地的对照组。** 之后任何复杂加权模型，都要证明能跑赢它，否则复杂度没换来价值。

**加权版（v1 再上）：** 在净值基础上叠加置信度权重、机构权重、时间衰减。

**大盘情绪分：** 各板块净值按品种数或持仓量加权，归一到 0–100，60 以上偏多、40 以下偏空。

### 三条口径规则（必须写进文档并固化）

| 规则 | 说明 |
|---|---|
| **一家一票** | 同一机构当天对同一品种发多篇，取最新一篇，不重复计票 |
| **NA ≠ 0** | 某品种当天没机构覆盖 → 记**缺失**，不记 0。记 0 会被误读成"大家都看中性" |
| **热度与方向分离** | 单独输出「今天多少家发了研报」。3 家看多和 30 家看多不该同权，覆盖家数是多空分的置信度 |

## 七、⑦ 呈现：交付什么

### 主交付：盘前推送（这才是产品的主体）

每日 8:00 推送到企业微信/飞书群，**三级结构，一屏看完**：

```
📊 大盘情绪 62 分（偏多）｜较昨日 +5｜较上周 +12
覆盖 28 家机构 / 96 篇研报

板块：有色 +45  黑色 +12  能化 −8  农产品 +3  贵金属 +30

变化最大：焦煤 +20 → +65（5 家转多）
分歧最大：原油（4 家看多 / 5 家看空）

[查看详情]
```

**推送策略：** 每日固定推一次，但**只在极值区或显著变化时加重提醒**（如大盘分突破 75/25，或单日变化超过 15 分）。中间区间天天喊「今天偏多」，两周就会被交易员静音——这是主动推送类产品的生死线。

### 辅交付：Web 看板

只做三个页面，不做多：

| 页面 | 内容 |
|---|---|
| **总览** | 大盘情绪分曲线 + 板块热力图 |
| **多空矩阵** | 机构 × 品种的表格，格子颜色标多空，**点格子弹出该机构该品种的证据原句** |
| **品种详情** | 单品种的情绪时间序列 + 覆盖家数 + 该品种历史观点列表 |

> **可解释下钻是刚需**，不是加分项。交易员看到「焦煤 +65」的第一反应一定是「谁说的、凭什么」，答不上来这个指标就没人用。

## 八、技术栈与部署

### 选型总表

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Python + FastAPI** | 解析、打分、调度全在 Python 生态，不要为了后端跨语言 |
| 调度 | **APScheduler**（进程内） | 单机定时够用；量级上来再换 Celery |
| 数据库 | **PostgreSQL 一个** | 结构化数据全放它，JSONB 字段存半结构化解析结果 |
| 对象存储 | 本地磁盘 或 MinIO | 存 PDF 原件 |
| 前端（MVP） | **Streamlit** | 一周能出可用看板，内部工具足够 |
| 前端（v2） | React + ECharts | 确认有人用了再重写 |
| 推送 | 企业微信 / 飞书机器人 Webhook | 无技术难点 |
| 部署 | **单机 Docker Compose** | 两个容器：app + postgres |

### 三个明确的「不做」

| 不做 | 为什么 |
|---|---|
| ❌ **向量数据库 / RAG** | 本项目**不做检索问答**，只做打分和汇总。上 Milvus 是纯粹的复杂度浪费。（如果后面要做「研报问答」，那是另一个产品） |
| ❌ **微服务拆分** | 一个 FastAPI 服务把全链路跑完，日均百篇的量级拆了只会增加联调成本 |
| ❌ **多 Agent 编排框架** | 这个链路是**固定流水线**，不是需要动态规划的任务。用 LangGraph 之类反而把简单流程搞复杂 |

## 九、数据库设计

五张表就够。

```sql
-- 1. 机构
org(id, name, short_name, weight, is_active)

-- 2. 研报（原件级）
report(
  id, org_id,
  title, publish_time, ingest_time,     -- ⭐ 两个时间戳，指标一律用 ingest_time
  source_channel,                        -- 官网 / 邮件 / 聚合站
  file_path, file_md5,                   -- ⭐ md5 去重
  parse_status, parsed_markdown,
  created_at
)
UNIQUE(file_md5)

-- 3. 观点块（切分后，一个机构 × 一个品种）
segment(
  id, report_id,
  product_code,                          -- 品种代码，NULL = 宏观/综述块
  sector,                                -- 板块
  raw_text,                              -- 原文块
  advice_text,                           -- 抽出的操作建议原句
  seq
)

-- 4. 打分（不可变，只追加）
score(
  id, segment_id,
  direction,          -- -2 ~ +2
  confidence,         -- 0 ~ 1
  evidence,           -- ⭐ 证据原句，下钻用
  method,             -- rule / llm / human
  model_version,      -- ⭐ 口径版本号，用于重算历史
  created_at
)

-- 5. 每日指标（可重算，聚合结果）
daily_index(
  trade_date,
  level,              -- product / sector / market
  key,                -- 品种代码 / 板块名 / 'MARKET'
  net_score,          -- -100 ~ +100
  bull_count, bear_count, neutral_count,
  coverage_count,     -- ⭐ 覆盖家数 = 热度，与方向分离
  calc_version,
  PRIMARY KEY(trade_date, level, key, calc_version)
)
```

### 三个设计要点

1. **`score` 表只追加不修改**，`daily_index` 可以按新口径重算——这样改口径时不用重跑昂贵的 LLM 打分。
2. **`model_version` / `calc_version` 双版本号**：打分口径和聚合口径分别管理，任何一个变了都能重算历史并对比新旧差异。
3. **`coverage_count` 独立成列**，不要只存净值——热度是方向的置信度，两者必须能分开看。

## 十、分阶段落地

| 阶段 | 范围 | 产出 | 大致工作量 |
|---|---|---|---|
| **MVP** | 3–5 家机构官网 + MinerU 解析 + 纯规则打分 + 净得分公式 + 企微推送 | 每天能推出一个数 | 2–3 周 |
| **v1** | 扩到 20+ 家（补邮件订阅）+ LLM 兜底打分 + 人工复核队列 + Streamlit 看板 | 可用的内部工具 | +4 周 |
| **v2** | 加权聚合 + 置信度 + 历史回溯验证 + 多空矩阵下钻 | 可对外说的产品 | +4 周 |

**MVP 阶段务必先跑通净得分公式这条最笨的路径。** 有了 baseline 和真实数据，才知道复杂模型该往哪个方向加——反过来先设计复杂模型，大概率是在解决不存在的问题。

## 十一、三个最大的风险

| 风险 | 后果 | 对策 |
|---|---|---|
| **用错时点** | 回测有未来函数，指标全部失真 | 全链路用 `ingest_time`，代码层面禁用 `publish_time` 做计算 |
| **切分错误** | 沪铜的观点算到沪铝头上，后面再准也没用 | 品种词典 + 标题层级双重锚定；多品种块单独标记；上线前人工抽检 100 块 |
| **指标跑不赢"数家数"** | 项目价值不成立 | MVP 就把净得分 baseline 建起来，每次迭代都跟它对比 |

## 附：一句话总结架构

**一条 Python 流水线 + 一个 Postgres + 一个推送机器人。** 复杂度全部集中在「按品种切分」和「多空判断」这两个真正难的环节，其余一律用最成熟最简单的方案。
