# Demo 迭代 Roadmap

> [03-架构方案.md](03-架构方案.md) 第十节那份 `MVP → v1 → v2` 是**生产版**路线图——
> 假设有真实数据源、有 API 预算、有真实用户。
> 这份是**演示版**路线图：目标不是把 demo 养成生产系统，而是让它在**离线、零依赖、3 分钟**的条件下，
> 尽可能完整地证明架构方案里的判断是成立的。
>
> 两条路线的取舍标准完全不同，因此分开写。生产版路线保持原样，不受本文影响。

---

## 一、判据

**目标函数：** 每一项迭代都要提升「让人在 3 分钟内相信这条链路是想清楚了才写的」，而不是提升功能数量。

### 四条硬约束（任何一项迭代都不得违反）

| 约束 | 为什么是红线 |
|---|---|
| **零第三方依赖、不联网、一键跑通** | 这是本仓库最稀缺的属性。`clone` 下来能跑，比数据是不是真的重要一个量级 |
| **不造假数据支撑结论** | 样本是虚构的，就不能拿它跑回测得出「指标有效」。造一个假 IC 出来，反噬远大于收益 |
| **诚实优先于完整** | 补不了的写清楚为什么补不了。[04 的已知局限清单](04-Demo说明.md#六-demo-与生产版的差异)是加分项，不要为了凑功能把它稀释掉 |
| **单项成本 ≤ 2 天** | 超过就拆或砍。作品集的边际收益衰减很快 |

### 优先级怎么排

按「**这一项能补上哪个会被当场问住的缺口**」排，不按链路顺序排。
一个功能做得再完整，如果它不对应任何一个会被追问的点，就排在后面。

## 二、路线图总览

| 阶段 | 主题 | 补的缺口 | 成本 | 优先级 |
|---|---|---|---|---|
| **R0** | 文档与代码对齐 | 文档比代码旧，有死链 | 0.5 天 | **必做，先做** |
| **R1** | 漏斗第 2 层：LLM 兜底 | 项目叫 Agent，但全链路 0 次模型调用 | 1.5 天 | **必做** |
| **R2** | 难例集 + 规则 vs LLM 评测 | 没有任何「模型好不好」的量化证据 | 1 天 | **必做** |
| **R3** | 漏斗第 3 层：人工复核回流 | 「数据飞轮」只在文档里，没有实现 | 0.5 天 | 建议做 |
| **R4** | 有效性验证方案（纯文档） | 唯一没法用代码回答的问题 | 0.5 天 | 建议做 |

合计 **约 4 天**。R0 → R1 → R2 有依赖，必须按序；R3、R4 可以并行插入或延后。

> **R1 和 R2 必须成对做。** 只做 R1 是「接了个 API」，价值很低；
> R1 + R2 才是「引入一层新方法，并用数据说明它带来了什么、代价是什么」——后者才是产品岗要看的东西。

## 四、R1 · 漏斗第 2 层：LLM 兜底（1.5 天）

### 为什么这是最该补的一项

项目名字里有 **Agent**，[架构方案第五节](03-架构方案.md#五-⑤-打分怎么判多空)画的是**三层漏斗**，
但 demo 只有第一层，全链路**零次模型调用**。这是简历筛和面试开场的必踩点：「你的 LLM 在哪」。

现在的答案（规则在这个场景性价比更高、完全可解释、可解释性是交易员的刚需）**本身是好答案**，
但「有实现 + 这个答案」和「只有这个答案」是两回事。前者是取舍，后者听起来像没做完。

接口位其实已经留好了（[`score.py` 的 `score_with_llm`](../sentiment/score.py)），现在是个只抛异常的占位。

### 怎么做才不破坏零依赖

**分两条路径，默认走离线：**

```
score_with_llm(text, provider=?)
  ├─ provider='fixture'（默认）→ 读 data/llm_cache/*.json 的录制结果 → 离线、零依赖、0.2 秒
  └─ provider='deepseek'        → urllib 手写 HTTP 调用 → 需要 --llm 显式开启 + 环境变量给 key
```

| 设计点 | 做法 | 理由 |
|---|---|---|
| HTTP 客户端 | 标准库 `urllib.request` 手写 | 不能引入 `requests`/SDK，红线 |
| 默认行为 | 走 fixture 回放 | `python3 run.py demo` 必须保持一键跑通、无需 key |
| 真实调用 | `run.py pipeline --llm` 显式开启 | 真调过 API 的证据留在 fixture 里，同时不强迫别人配 key |
| 缓存键 | 观点块文本的 MD5 | 与采集层的去重口径一致，同一句话不重复花钱 |
| 输出约束 | 强制 JSON `{direction, confidence, evidence}` | 架构方案第五节的硬要求，**证据原句是可解释下钻的唯一来源** |
| 失败兜底 | 超时 / JSON 解析失败 → 退回规则层结果并标低置信度 | 不能因为 API 抖动就让当天的指标缺一块 |
| 落库 | `score.method='llm'`，`model_version` 记具体模型与日期 | `score` 表只追加，口径可回溯 |

### ★ 顺带激活一个一直在空转的设计

引入第二层后，`SCORE_VERSION` 从 `rule-v1` 变成 `hybrid-v1`（含义是「这一版打分**策略**」，
不是「哪个模型」；具体来源由 `score.method` 的 `rule / llm / human` 区分）。

于是库里会**同时存在两个 `model_version` 的指标行**，
而 `daily_index` 的主键 `(trade_date, level, key, model_version, calc_version)` 正好支持二者并排对比——

**「双版本号」这个设计从「文档里写着」第一次变成「库里用着」。**
现在库里只有 `rule-v1` / `netscore-v1` 一种组合，这个卖点是空转的。
R1 之后可以直接演示：同一天、同一批研报，`rule-v1` 打分口径算出 65.5 分，`hybrid-v1` 算出多少分，差在哪几个品种。

**验收：** `python3 run.py demo` 仍然零依赖、离线、一键跑通；
终端能并排打出 `rule-v1` 与 `hybrid-v1` 两套指标；`--llm` 能真实调通一次并把结果录进 fixture。

## 五、R2 · 难例集 + 规则 vs LLM 评测（1 天）

### 为什么必须跟着 R1 一起做

[04 的已知局限 #1](04-Demo说明.md#已知局限诚实列出) 已经承认：
**99.6% 的规则命中率是虚高的**，因为样本数据是照着规则表写的，真实研报预期只有 60–70%。

这句话现在只是一个诚实的声明，**没有任何证据**。R2 就是把它变成有证据的：
造一批规则表故意吃不下的难例，看规则层会错成什么样、LLM 层能不能接住。

### 产出物一：难例集（这是核心资产，不是测试数据）

新建 `data/hardcases/`，40–60 条真实研报里常见、但当前规则表覆盖不到的表述，每条带人工标注方向。

来源应当**覆盖四类**，每一类都对应一个具体的失败模式：

| 类别 | 例子 | 规则层为什么会挂 |
|---|---|---|
| 条件句 | 「若跌破 3800 则转空，否则维持震荡」 | 方向依赖条件，词表无法表达 |
| 长距离否定 | 「短期虽有回调压力，但中期不改多头格局」 | 转折词后才是真正的结论 |
| 隐含方向 | 「建议关注逢低买入机会」「下方支撑较强」 | 没有任何方向词，靠语义 |
| 多空并陈 | 「多单减持、空单轻仓试探」 | 一句里两个方向，要判净方向 |

> 这批数据本身就是产出物：它是[架构方案第五节](03-架构方案.md#五-⑤-打分怎么判多空)里「人工复核结果回流成标注集」的**起点**，
> 也是 R3 的评测底座。

### 产出物二：三方对比表

在难例集上跑 `规则判定 × LLM 判定 × 人工标注`，输出：

- **准确率 / 混淆矩阵**，规则层与 LLM 层分开算
- **规则层命中率的真实数字**——预期会从 99.6% 掉到 60–70% 区间，**这个下跌本身就是最有说服力的结果**，它证明了局限 #1 那句话不是随口说的
- **分歧样本逐条列出**：规则对 LLM 错的、LLM 对规则错的，各挑几条，写清楚为什么

新增 `python3 run.py eval` 一键出这张表。

### ★ 这一项的真正价值

大部分作品集会写「我引入了 LLM，效果更好了」。
这一项能让你写的是：「**我引入了 LLM，在难例集上准确率从 X 提到 Y，但延迟从 0.2 秒变成 N 秒、单日成本约 Z 元，
所以生产版的设计是规则兜住 60–70% 的量、LLM 只吃剩下的**」——
这才是架构方案第五节「三层漏斗」这个设计成立的**依据**，而不是一句主张。

**验收：** `run.py eval` 能出三方对比表；能用一句话回答「LLM 比规则好多少、代价是什么」，且这句话背后有数。

## 六、R3 · 漏斗第 3 层：人工复核回流（0.5 天）

第三层现在只存在于文档里。实际上底子已经有了——
`confidence < LOW_CONFIDENCE(0.6)` 的行天然就是复核队列，当前样本里有 **9 条**。缺的是闭环。

| 做什么 | 说明 |
|---|---|
| `python3 run.py review` | 依次弹出低置信度观点块：原文 + 抽出的建议句 + 当前判定，人工输入方向 |
| `human_label` 表 | 记录人工判定、复核人、时间；`score` 表追加一行 `method='human'`（**不修改原行**） |
| 回流 | 人工标注攒进难例集，成为 R2 评测集的增量；标注量在终端可见 |

**为什么值得做：** 「数据飞轮」是 AI 产品岗的高频追问。
有一条能跑的 `review` 命令，回答就从「我们设计了回流机制」变成「你可以跑一下，标 3 条，再跑 eval 看评测集变大」。

**验收：** 复核过的块不再重复出现在队列里；`score` 表能看到同一 `segment_id` 上 `rule` 和 `human` 两行并存。

## 七、R4 · 有效性验证方案（0.5 天，纯文档）

### 这一项明确不写代码

「这个情绪指标到底有没有用」是整个项目最重要的问题，
但**当前条件下无法诚实地回答**：3 个交易日 + 全虚构样本，跑不出任何有统计意义的结论。

硬做的话就是造一个假 IC。懂量化的面试官一眼识破，**反噬远大于收益**。这条撞的是第二条红线。

### 改成写清楚「如果有数据，会怎么验」

新增 `docs/06-有效性验证方案.md`，内容对应[调研文档 01 第 3.3 节](01-开源项目技术调研.md)：

| 章节 | 要写清楚 |
|---|---|
| 分档前瞻收益 | 按情绪分分 5 档，看未来 1/3/5 日收益的单调性，怎么算、看什么 |
| IC / RankIC | 计算口径、显著性判据、多少样本才够（**至少 1 年、20+ 家机构**的量级说明） |
| 中性化检验 | 对「研报数量」「品种波动率」做回归取残差——**排除掉「情绪分只是研报数量的代理变量」这个致命解释** |
| 判优标准 | 相对 baseline（一家一票只数家数）的提升幅度到多少才算模型有增量 |
| `BEAR_WEIGHT` 定标 | 怎么用历史数据定这个系数，而不是拍一个 1.3 上去（对应[已知局限 #3](04-Demo说明.md#已知局限诚实列出)） |

**验收：** 别人拿着这份文档 + 一年的历史数据，能直接开跑，不用再问你任何问题。

## 八、明确不做（和「做什么」同等重要）

| 不做 | 判断依据 |
|---|---|
| ❌ **真实数据源（官网爬虫 + IMAP 订阅）** | ① 砸掉零依赖/离线/一键跑这条红线；② 公开仓库放真实研报与[已声明的脱敏立场](../README.md)自相矛盾；③ 爬虫会烂——半年后官网改版，别人打开就是 404，**比没有更糟**；④ 采集不是本项目的难点，架构方案自己写了难点在切分和判多空 |
| ❌ **Streamlit 看板** | 已经有更好的东西了：自包含 HTML，双击就开、能悬停下钻到证据原句。Streamlit 反而要 `pip install` + 起服务。R0 第 5 项（挂 GitHub Pages，10 分钟）在同一目标上收益高一个量级 |
| ❌ **真的跑回测** | 见 R4。数据不支持，硬做即造假 |
| ❌ **微调模型 / 向量库 / 多 Agent 框架** | [架构方案第八节](03-架构方案.md#八-技术栈与部署)已经论证过为什么不做。这里再上，等于推翻自己刚立的取舍——**取舍的一致性本身就是被考察的东西** |
| ❌ **扩品种词典 / 加更多样本研报** | 边际收益近乎为零。45 个品种、27 篇研报已经足够说明链路成立，加到 70 个品种不会让任何人多信一分 |

## 九、每一项对应哪个提问

排优先级的实际依据，摊开写：

| 阶段 | 补上后能回答 |
|---|---|
| R0 | —（不补会被扣分，补了不加分） |
| R1 | 「这项目叫 Agent，AI 在哪？」「为什么不直接全用大模型？」 |
| R2 | 「你怎么知道规则够用？」「引入 LLM 的收益和代价各是多少？」「99.6% 命中率是不是刷出来的？」 |
| R3 | 「模型怎么持续变好？」「标注从哪来？」 |
| R4 | 「这个指标到底有没有用，你怎么证明？」 |

**R2 和 R4 是这里唯一两个「产品岗专属」的问题**，工程师候选人通常答不好。
这也是它们优先级高于「多接一个数据源」的根本原因。

## 十、时间不够时的降级路径

| 可用时间 | 做什么 |
|---|---|
| **半天** | 只做 R0。文档对齐 + GitHub Pages。**不要用半天去动代码** |
| **1 天** | R0 + R4。两项都是文档，但补的是最大的两个说服力缺口 |
| **2.5 天** | R0 + R1 + R2。功能上的核心补完，**不要只做 R1 不做 R2** |
| **4 天** | 全做 |

> 如果四天都没有：**保持现状是完全可接受的**。
> 当前 demo（27 篇 → 227 块 → 三级聚合 → 推送 + 看板，181 个测试全过，局限逐条列清）
> 已经能撑住一轮完整的项目深挖。这份 roadmap 补的是上限，不是及格线。
